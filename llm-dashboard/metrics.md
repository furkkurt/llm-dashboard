# Metrics for LLM Code Quality Evaluation

## Overview

To evaluate the quality of code generated by Large Language Models (LLMs) across Kotlin and Flutter/Dart ecosystems, we employed a set of cross-language software metrics that are objectively measurable, well-established in software engineering literature, and obtainable from existing static analysis tools in our pipeline (Detekt for Kotlin, Dart analyzer for Flutter). These metrics provide a lightweight yet academically rigorous foundation for comparing LLM outputs while preserving the existing faithfulness evaluation components.

## Selected Metrics

We selected five core metrics that satisfy the requirements of cross-language comparability, academic validity, and minimal implementation overhead:

### 1. Average Cyclomatic Complexity
**Definition**: Measures the number of linearly independent paths through a program's source code, serving as an indicator of code complexity, testability, and potential defect proneness.
**Application**: Computed as the average cyclomatic complexity across all functions/methods in generated code. Obtained directly from Detekt's `cyclomaticComplexity` metric for Kotlin and Dart analyzer's equivalent measurement for Flutter/Dart code. Lower values indicate simpler, more testable code.

### 2. Lines of Code (LOC) and Comment Ratio
**Definition**: LOC quantifies code size, while comment ratio (comment lines divided by total lines) measures documentation effort.
**Application**: Raw LOC provides size normalization for other metrics. Comment ratio indicates investment in code maintainability and readability. Both metrics are trivially extractable from lexer/AST processing in both Detekt and Dart analyzer outputs.

### 3. Halstead Volume and Difficulty
**Definition**: Volume estimates program size based on unique and total operators/operands; Difficulty estimates the mental effort required to understand or write the code.
**Application**: Derived from token counts of operators (+, -, if, for, etc.) and operands (variables, literals) in the source code. Both metrics are available from Detekt and computable for Dart using its tokenizer facilities. Volume indicates code size; Difficulty correlates with cognitive load during development.

### 4. Maintainability Index (MI)
**Definition**: A composite metric combining LOC, cyclomatic complexity, and Halstead volume (higher values indicate better maintainability).
**Application**: Calculated using the standard formula:  MI = 171 - 5.2 * ln(Volume) - 0.23 * (Cyclomatic Complexity) - 16.2 * ln(LOC) + 50 * sin(sqrt(2.4 * perCM))
where perCM represents the percentage of comment lines. This index provides a single-number maintainability proxy widely used in both industry tools and academic research.

### 5. Average Nesting Depth
**Definition**: Measures the maximum depth of nested control structures (if/for/while/try blocks), serving as a proxy for cognitive complexity and readability challenges.
**Application**: Computed by traversing the abstract syntax tree to track nesting levels, then averaging the maximum depth across functions/methods. Available from Detekt's `nestedBlockDepth` metric and implementable via AST walk in Dart analyzer. Lower values indicate flatter, more readable code structure.

## Implementation Approach

These metrics were integrated into our existing evaluation pipeline with minimal disruption to established workflows:

1. **Tool Utilization**: Leveraged existing static analysis runners (`run_detekt.py` and `run_dart_analyze.py`) already present in the project, requiring only lightweight post-processing to extract the target metrics.

2. **Data Extraction**: Added metric-specific parsers to convert tool outputs (Detekt XML, Dart analyzer JSON/metrics) into standardized numerical values stored alongside existing analysis results.

3. **Model Extension**: Updated the `PaperScores` data model to include fields for each new metric while preserving all existing faithfulness-related fields and scoring mechanisms untouched, per requirements.

4. **Result Storage**: Merged newly extracted metrics with existing analysis data before persistence to the database. The dashboard declares a **winner** from **`quality_composite_0_100`** in `paper_scores`, not from the legacy `composite_default_0_100` blend. That composite is implemented in `backend/paper_scoring.py` (`attach_quality_composite`): **Maintainability Index** (clamped to [0, 100], missing → neutral 50), **nesting** score `max(0, min(100, 100 − 15 × avg_nesting_depth))` (missing → 50), **analyzer cleanliness** (same linear penalty as static-analysis health: 12×errors + 3.5×warnings + 0.8×infos, capped 0–100), and **faithfulness** (0–100) **only when rated**; if faithfulness is absent, the first three weights (**0.30 / 0.10 / 0.30**) are renormalized to sum to 1.0.

5. **Heuristic cross-language extraction**: When building `AnalysisMetrics`, `backend/metrics_util.py` calls `backend/cross_language_metrics.compute_cross_language_metrics` on the source string to supply LOC, comment lines, Halstead-style measures, cyclomatic complexity, nesting depth, and MI in a toolchain-consistent way alongside Detekt / Dart analyzer outputs.

6. **Kotlin platform note**: Standalone **kotlinc** runs only for JVM-style Kotlin without Android framework imports (`android.*`, `androidx.*`, `com.google.android.*`); such snippets skip JVM compilation in the temp sandbox (no Android SDK). **Detekt** still runs. This bounds what “compilability” means for mobile-oriented snippets (see `manual.md` §1).

## Academic Justification

This metric selection addresses key dimensions of code quality valued in software engineering research:

- **Correctness Proxy**: Cyclomatic complexity and nesting depth correlate with test effort and defect density
- **Maintainability**: LOC, comment ratio, Halstead metrics, and Maintainability Index collectively assess long-term code health
- **Cognitive Dimensions**: Nesting depth and Halstead Difficulty capture readability and mental effort aspects
- **Cross-Platform Validity**: All metrics have established definitions independent of language-specific idioms, enabling fair Kotlin/Dart comparisons
- **Research Reproducibility**: Reliance on well-documented, tool-generated metrics ensures reproducibility across studies

The approach maintains faithfulness evaluation as a separate, orthogonal dimension while adding quantifiable, tool-based code quality measures suitable for empirical analysis in academic publications. These metrics provide actionable insights beyond binary success/failure rates, enabling nuanced comparisons of LLM-generated code quality across different models, prompting strategies, and temperature settings.
